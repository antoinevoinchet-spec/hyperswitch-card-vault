# Audit log: design

Date: 2026-11-20. Branch: `feat/audit-log` (from `main`, `42ee89a`). Status: draft, awaiting owner approval.

## Intent

This fork is a study project. The goal is to understand and show how a vault holding sensitive data
keeps a trace of every access to it (who did which operation, when, with which outcome) without ever
copying the protected data into that trace.

## Current state (read in the code on 2026-11-20)

- No audit code exists (`grep -rni audit src` returns nothing).
- HTTP framework: axum. Handlers receive extractors; `TenantStateResolver` reads `x-tenant-id` and
  returns the tenant's `TenantAppState` (database pool, config).
- With the `middleware` feature, the JWE middleware decrypts the body before the handler runs. Request
  identifiers (merchant, customer, reference) are only readable inside handlers.
- `x-request-id` is set by `MakeUuidV7` when absent and propagated when the caller sends one.
- There is no per-person authentication: the caller is identified by its tenant and its JWE key.
- Under the `key_custodian` feature, a tenant's `TenantAppState` (and so its database pool) only exists
  after a successful `/custodian/decrypt`.
- Upstream already treats some identifiers as masked values: `locker_id` is stored as `Secret`, and the
  v2 responses wrap `vault_id` in `Secret`.
- PR CI has neither PostgreSQL nor Redis, and runs `cargo hack check --each-feature`.

## Decisions taken by the owner (2026-11-20)

1. Scope of logged operations: **every operation except `/health`**.
2. Storage: **a dedicated PostgreSQL table**, written behind a replaceable sink interface.
3. Audit write failure: **fail-closed**. The operation's response is replaced by an error and no data
   leaves the vault without a trace.
4. Tamper evidence: **no hash chaining in this version**. The table is append-only from the code's
   point of view. Chaining is listed as a next step.
5. No configuration switch: **the audit log is always on**. No file under `config/` changes.

## Approaches considered

- Storage: the PostgreSQL table (chosen) gives a write result the code can check and a log the vault can
  query. A structured log stream would scale better and cost nothing, but a lost line raises no error,
  which makes fail-closed impossible. The long-term path keeps the table and adds a second sink that
  copies entries to an external write-once store (outbox pattern).
- Where to hook: a tower layer around the router (rejected: with `middleware` it only sees encrypted
  bodies, and it cannot read merchant or reference identifiers); a call at the end of each handler
  (chosen: it sees the decrypted identifiers and the typed result, and can block the response).

## Requirements

Each requirement is numbered so the plan can point to it.

- **D1. One entry per audited operation, success or failure.** Audited operations, with their
  `operation` value:

  | Route | `operation` |
  |---|---|
  | `POST /data/add`, `POST /cards/add` | `locker_add` |
  | `POST /data/retrieve`, `POST /cards/retrieve` | `locker_retrieve` |
  | `POST /data/delete`, `POST /cards/delete` | `locker_delete` |
  | `POST /data/fingerprint`, `POST /cards/fingerprint`, `POST /api/v2/vault/fingerprint` | `fingerprint` |
  | `POST /api/v2/vault/add` | `vault_add` |
  | `POST /api/v2/vault/retrieve` | `vault_retrieve` |
  | `POST /api/v2/vault/delete` | `vault_delete` |
  | `POST /entity` | `entity_create` |
  | `POST /key/transfer` (feature `external_key_manager`) | `key_transfer` |
  | `POST /custodian/decrypt` (feature `key_custodian`), on success | `custodian_decrypt` |

  Once the handler body has run, it writes exactly one entry with the outcome. A business error
  (unknown merchant, reference not found, validation error) is recorded as a failure with its code.
  Verifiable by: unit tests on the audit recording function (success and failure results), and one
  call site per row of the table, visible in the diff.

- **D2. An entry holds metadata only.** Fields, each with why it exposes no protected data:

  | Field | Type | Why it is not protected data |
  |---|---|---|
  | `audit_id` | `VARCHAR(64)`, UUID v7 generated by the vault | random value, derived from nothing in the request |
  | `created_at` | `TIMESTAMP`, UTC | the clock, not request data |
  | `request_id` | `VARCHAR(64)`, nullable | stored only if the `x-request-id` header parses as a UUID; any other value becomes NULL, so a caller cannot smuggle free text into the log |
  | `tenant_id` | `VARCHAR(64)` | header already validated against the list of known tenants |
  | `operation` | `VARCHAR(32)`, fixed values from D1 | chosen by the code, never by the caller |
  | `merchant_id` | `VARCHAR(255)`, nullable | merchant id (v1) or entity id (v2) from the request body, a technical identifier the owner listed as allowed |
  | `customer_id` | `VARCHAR(255)`, nullable | `merchant_customer_id` from the request body (v1 only), a technical identifier the owner listed as allowed |
  | `resource_id` | `VARCHAR(255)`, nullable | `card_reference` (v1) or `vault_id` (v2) from the request body, or the reference returned by an add: the identifier of the stored object, not its content |
  | `outcome` | `VARCHAR(16)`: `success` or `failure` | chosen by the code |
  | `status_code` | `SMALLINT` | HTTP status of the result |
  | `error_type` | `VARCHAR(64)`, nullable | name of the `ApiError` variant (for example `NotFoundError`), a fixed string from the code; the variable message is not stored |

  Never stored: card data, the `data` payload, decrypted or encrypted content, keys, `master_key`,
  custodian keys, fingerprint keys or values, fingerprint ids, batch labels, JWE bodies, headers other
  than the tenant and request ids. The entry type implements `Debug` and `Serialize` only over the
  fields above. Merchant, customer and resource ids are chosen by the caller, so a misused field could
  hold a card number: any id that is 13 to 19 digits once spaces and hyphens are removed, and passes the
  Luhn checksum, is stored as `redacted` (builder's call, added after the second-opinion review).
  Verifiable by: a test that builds an entry from a request containing the test card number
  `4111111111111111`, serializes it to JSON and asserts that the number is absent from the output.

- **D3. Fail-closed.** If writing the entry fails, the handler returns
  `ApiError::DatabaseInsertFailed("audit_log")` (HTTP 500) instead of its normal response. For a read,
  the decrypted data is never returned. For an add or a delete, the database change has already
  happened. The caller receives an error and may retry: an add reuses the existing record (duplicate
  check), and a delete of an already-deleted reference changes nothing.
  For `/custodian/decrypt`, the entry is written with the newly built tenant state *before* that state is
  published with `set_app_state`. If the write fails, the state is dropped and the tenant stays locked,
  so the vault is never unlocked without a trace (builder's call, following decision 3).
  Verifiable by: a unit test with a sink that always fails: the recording function returns the error
  and not the successful value.

- **D4. UTC timestamps.** `created_at` comes from `utils::date_time::now()`, which is UTC.
  Verifiable by: code review (single call site) and a test asserting the entry timestamp lies between
  two `now()` readings.

- **D5. Append-only interface.** The sink trait (`AuditInterface`) exposes one write method,
  `insert_audit_entry`. There is no update, delete or read method in this version.
  Verifiable by: the trait definition in the diff.

- **D6. Schema.** A new migration folder `migrations/2026-11-20-000000_create_audit_log/` creates the
  `audit_log` table (D2 columns, primary key `audit_id`, an index on `created_at`). `down.sql` drops it.
  Existing migrations are untouched. `src/storage/schema.rs` gains the matching `diesel::table!`.
  Verifiable by: `git diff --name-only main -- migrations` lists only the new folder.

- **D7. Direct PostgreSQL writes, also with `kv`.** The audit insert always goes to PostgreSQL through
  `Storage::get_conn()`, never through the Redis KV path, so an entry cannot be lost in a Redis outage.
  Verifiable by: the `AuditInterface` implementation has no `#[cfg(feature = "kv")]` branch.

- **D8. Operations that cannot reach the table.** Before `/custodian/decrypt` succeeds, the tenant has
  no database pool, so `/custodian/key1`, `/custodian/key2` and a failed `/custodian/decrypt` cannot be
  written to the table. Requests rejected before the handler runs cannot be written either: unknown
  tenant, JWE decryption failure, malformed JSON. For the custodian routes, the vault emits a
  WARN-level `tracing` event marked with the field `audit = true` (WARN so the default log filter keeps
  it) and the same metadata fields (operation, tenant, outcome), never
  the key. Rejections before the handler are left to the existing request logs and are listed as a
  known limit. Second known limit: with the `middleware` feature, the response is encrypted or signed
  after the handler returns. If that step fails (`ResponseMiddlewareError`, HTTP 500), the entry already
  says `success`. The middleware cannot read the decrypted identifiers, so moving the hook there is not
  worth it in this version.
  The scope "except `/health`" covers `/health`, `/health/diagnostics` and `/health/runtime-config`.
  Verifiable by: the three custodian call sites in the diff; the limits are written in this document.

- **D9. Always on.** No configuration key is added.
  Verifiable by: `git diff --name-only main -- config` is empty.

- **D10. Quality gates.** `cargo build -j 4` and `cargo test -j 4` exit 0 with at least 21 tests
  passing. `cargo clippy --all-features --all-targets -j 4` reports no warning. CI on the PR passes,
  including `cargo hack check --each-feature --all-targets`, so new tests must also compile with each
  feature enabled on its own.
  Verifiable by: the command outputs and `gh pr checks`.

- **D11. License notice.** `README.md`, section "Changes from the original", names every file changed
  on the branch.
  Verifiable by: comparing `git diff --name-only main` with that section.

- **D12. No compliance claim.** No added line, in code or docs, contains any of the forbidden
  compliance phrases listed in the owner's completion criteria (see the "No compliance claim" rule in
  `CLAUDE.md`). This document and the plan refer to them without quoting them, so the check also
  passes on the docs.
  Verifiable by: the owner's `grep -ciE` command on `git diff main` returns 0.

## Non-goals

- Querying the audit log through an API.
- Retention, purging, partitioning by month.
- Hash chaining, signatures, or an external write-once copy.
- Logging requests rejected before the handler (D8).
- Per-person identity: the vault has no user accounts.

## Anti-goals (would make this a failure even if it works)

- Any protected value appearing in an entry, a log line or a test output.
- An audited read that returns data while its entry was not written.
- A change to the behaviour of existing routes when the audit write succeeds.

## Next steps (not built here)

- Second sink copying entries to an external write-once store (outbox), then hash chaining anchored
  outside the database.
- Partitioning `audit_log` by month and a retention job.
- Database-level append-only enforcement (revoke `UPDATE` and `DELETE` on `audit_log` for the
  application role).

## Left to the builder

- Module layout (for example `src/audit.rs` plus an `AuditInterface` in `src/storage.rs` and its
  `Storage` implementation in `src/storage/db.rs`), names of internal types and helpers.
- How each handler is split so the result can be recorded before it is returned (for example an inner
  function returning the result, wrapped by the public handler).
- The new `error` type for the audit sink, following the existing `*DBError` pattern.

## Sources used for the design

- HashiCorp Vault audit devices: fail-closed when no device can write; values HMAC-hashed.
  https://developer.hashicorp.com/vault/docs/audit
- Basis Theory logs (tenant, entity type and id, operation, timestamp; reads logged).
  https://developers.basistheory.com/docs/api/logs
- Skyflow audit events (actor, action type, resource ids, response code, request id).
  https://docs.skyflow.com/api/data/audit/list-data-audit-events
- AWS KMS with CloudTrail (plaintext omitted from logs; signed digest files).
  https://docs.aws.amazon.com/kms/latest/developerguide/logging-using-cloudtrail.html
- PCI DSS v4.0.1 requirement 10.2, from secondary sources only (official text not read):
  https://withpci.pages.dev/requirements/10/10.2/10.2.2
